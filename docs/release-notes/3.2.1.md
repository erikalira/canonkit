# canonkit 3.2.1

**Action required: none.** Existing installations keep working. Re-run
`npx canonkit@3.2.1 install` with your existing target flags to pick up this release.

## For users

### Safer `tool add` in repositories you do not trust

Closes the follow-ups of [issue #36](https://github.com/erikalira/canonkit/issues/36).
Opening an untrusted repository and running `canonkit tool add` no longer lets
that repository run code or stall the command:

- **Git runs without repository-chosen code.** The `.gitignore` tracked-files
  note and the graphify git-hooks preflight now run git with the repository's
  `core.fsmonitor` disabled and without any inherited `GIT_*` variable, as
  `git-ignore-sandbox-files` already did. The preflight still reads the real
  `core.hooksPath`, so a hook manager is still detected.
- **No hang on special files.** `.gitignore`, git hook files, `.claude`
  settings and legacy activity logs are read only when they are regular files.
  A FIFO or device there is refused or treated as unreadable instead of
  blocking the command forever.
- **Every path segment is checked.** Before setup runs, each existing directory
  on the way to a write target must be a real directory, not only the first:
  a symlinked `.claude/skills` inside a real `.claude` is now refused, and an
  existing file target that is a symlink is refused too. Nothing runs when a
  check fails.

Repositories with ordinary files and directories see the same output as before.

### Guided install flags a tool that is not installed

In the guided `install`, Graphify and OpenSpec are preselected only when their
binary is found. A missing one starts unselected and shows
`(recommended, not installed)`. If you select it anyway, install prints how to
install it right away, before anything is written, and skips that tool; the
rest of the install continues and does not end as failed. The review screen
lists the tool as skipped, and the final report lists it as not installed.
Install the tool, then run `npx canonkit tool add <tool>`. Explicit `--tool` flags are
unchanged: a missing binary still fails that tool.

### User and project wording in maintenance commands

`doctor`, `uninstall`, `models` and the security diagnostics now use the same
**user level** / **project** terms as the guided install, instead of
"global"/"repository". The short `doctor` report groups its general checks
under "User level" and "This project"; the Security block, the exit code and
`doctor --verbose` are unchanged. `uninstall` says which level it removes and
what it keeps at the other one.

The README, the installation reference and the reasons shown in the install's
security review use the same terms. The recommended-settings table and the install
review's scope label now say `project` (the review showed `REPOSITORY`). The installation reference section is now
"Native security, per project"; links to the old
`#native-security-per-repository` anchor still work.

### Incidental findings go to the project's backlog

A concrete problem found outside the current task now goes to the backlog your
project already uses: a file such as `todo.md`, `TODO.md` or `BACKLOG.md`, or
its tracker. GitHub issues are used only when that is the project's backlog;
before, the procedure offered GitHub issues by default. With no identifiable
backlog, the findings stay in the final report and no file is created.

- **File backlog:** you see numbered entries with the exact lines and where
  they go, approve once, and they are written with the file-edit tool. Nothing
  is committed. A tracked backlog file is published with your next push, so
  entries are sanitized.
- **Tracker:** the review and approval flow is unchanged.
- **Security stays private.** Exploitable vulnerabilities, exposed secrets and
  sensitive incidents never go into a repository's backlog file or a public
  issue; they use the project's private reporting channel.

This changes the managed `AGENTS.md` block and the `orchestrate` skill, both
picked up by re-running install, as at the top of these notes. Nothing changes until you
authorize an entry.

### What to do when the sandbox blocks a site

With canonkit's strict network lock, a site outside the allowed list fails
with `403 host is not on the allow list`, and agents had no guidance on what to
do next. The managed Claude Code block now tells them to report the blocked host
and the setting to change, without retrying through another tool and without
editing settings themselves. The change goes in one of two places:

- **Only WebFetch needs the site:** `WebFetch(domain:<host>)` in the project's
  `permissions.allow`. Shell commands stay blocked.
- **A shell command needs it:** the host in `sandbox.network.allowedDomains` in
  `~/.claude/settings.json`. A project's `allowedDomains` has no effect under the lock.
  A `WebFetch(domain:<host>)` rule in user settings also opens the shell to that host.

Allow exact hosts you trust to receive project data, never wildcards. The
installation reference has a new
[Allowing a destination](../install.md#allowing-a-destination) section with the
cautions. Re-run
install, as at the top of these notes, to pick up the block.

### New `backlog-cycle` skill

`/backlog-cycle` in Claude Code, `$backlog-cycle` in Codex. It runs one item of
the backlog your project already uses per session: it picks the item, confirms
on disk that it still exists, classifies the risk and sizes the planning, and
stops for your approval before any edit. Then it implements, verifies before
review, reviews, closes out, asks how you want to commit (the lead commits, only
the message, or the ready command) and hands over a prompt for the next session.
If the item does not close (a veto, an item that is really several, an obsolete
one), it stops and records the real state instead of leaving a half-done change.

- **Only when you call it.** It never loads or runs on its own, so it adds
  nothing to sessions where you do not use it.
- **No assumptions about your project.** It needs no specific backlog file,
  planning tool or release scheme; it never creates a backlog.
- **No commit or push before you answer.**

It is installed with the other user-level skills when you re-run install, as at
the top of these notes.

### Faster reviewer briefs

The `orchestrate` skill now tells the lead to put the resolved diff scope in
every reviewer's brief: the revision range (`<base>..<head>`, or working tree
against HEAD), the exact diff command, and the changed files with their line
counts, with untracked files listed separately. A reviewer such as Quinn or Gard can start by
reading the diff instead of working out what changed. For a large diff, the
brief gives one diff command per file so the reviewer reads it in parts. No file
is added to your repository.

Quinn, Gard, Archie and Perry now read code and diffs by range: they start from
the brief's diff and file list, batch independent read-only commands into one
call, and read only the span a search located, reading more when a finding needs
the surrounding context. The speed effect is unmeasured: it stays unconfirmed
until dispatch telemetry before and after is compared (`docs/telemetry.md`:
`duration_ms`, `tokens`, `tool_uses`, `report_chars` and the subagent
`tool_result` characters).
