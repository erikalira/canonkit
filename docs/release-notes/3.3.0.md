# canonkit 3.3.0

**Action required: none.** Existing installations keep working. Re-run
`npx canonkit@3.3.0 install` with your existing target flags to pick up the new
dashboard and hook fields. Nothing below changes unless you open the dashboard or
opt in to the telemetry read exception.

## For users

### Execution Graph and Timeline in the dashboard

The local dashboard (`node ~/.claude/canonkit-dashboard/serve.js`, then
`http://localhost:4317`) now opens on an **Execution Graph**: the dispatches and
gates that the Claude Code hooks recorded for a session, as a navigable graph,
with a filterable **Timeline** beside it. Selecting a timeline entry selects and
frames its node; selecting a node shows its source, measurements and what is
unknown. The previous dispatch and token view is still there as **Activity**.

It shows only what the hooks observed, and says so:

- **Unknowns stay unknown.** The hooks do not record project, worktree or
  branch, so the dashboard shows "Project not identified" instead of guessing
  from a folder name. A stop event that cannot be linked to exactly one dispatch
  stays a separate observation instead of being attached to a guess.
- **Gates show their decision.** Allowed, confirmation-requested and blocked
  gates are labeled as such; a confirmation request is not shown as an approval.
- **Reference routes are separate.** The LOW/MEDIUM/HIGH routes are a reference
  view; none is presented as the path a session took.
- **Passive and local.** It binds to 127.0.0.1, accepts only loopback requests
  from its own origin, and has no buttons that run commands or approve anything.
  When polling fails it keeps the last snapshot with a stale-data notice and
  retries.

Without hook registrations (`npx canonkit install --wire-hooks`) there is
nothing to show; the dashboard does not create telemetry itself. The published
package ships the compiled frontend and runs with Node alone; from a source
checkout, run `npm run dashboard:build` first. Codex, OpenCode and Copilot are
not instrumented yet; the planned views that build on this (project identity,
workflow milestones, other runtimes, the Agent Office) are tracked in
`CANONKIT_ROADMAP.md`. [What it records and its limits](../telemetry.md#dashboard).

### Dispatch cost fields in the activity log

`agent_start`, `agent_resume` and `agent_end` lines now carry what a dispatch
costs, as lengths and numbers only, never text: `brief_chars`,
`message_chars`, `tokens.first_call` (the cold-start floor),
`tokens.cache_creation_5m` / `cache_creation_1h`, and `complete` on background
dispatches.

**Earlier totals are underestimates.** Before this release a background
dispatch could lose its `report_chars` and its final API call when the
subagent's last transcript entry landed after `SubagentStop`. The hook now
waits up to 1.5 s for it, only when it is missing, and marks the line
`complete: false` if it never appears. Do not compare logs from before and after
this release without accounting for that. [Stable fields](../telemetry.md#stable-fields).

### Optional: let sandboxed commands read telemetry

Under the strict sandbox, commands cannot read `~/.claude/canonkit-activity`, so
running the dashboard or reading telemetry from a sandboxed shell failed. The
**No, customize** review of `canonkit install` now offers a read exception for
that folder, with "Keep closed" preselected. With it, every sandboxed command
can read session IDs, project names, agent names and the paths of files that
gates flagged; that is why it is never added by *Yes*, `--recommended`, `--yes`,
dry runs or runs without a terminal. `uninstall` removes it, and with the
sandbox enabled `canonkit doctor` reports its state.
[Sandboxed commands](../telemetry.md#sandboxed-commands).

### Progressive loading guidance for web screens

Bob and Pixie, and the React and UI-review stack packs, now treat progressive
rendering as the default when a route or screen is created or substantially
changed and it loads data the first screen does not need: wait only for the
essential data, fetch independent sources in parallel, defer the rest, and give
each deferred part its own fallback and error state. Pixie's handoff names what
the first screen needs and what may arrive later. Untouched routes and LOW fixes
are not retrofitted. Long image lists and grids load above the fold first: only
first-screen items request images in the server HTML, the rest mount near the
viewport (IntersectionObserver), and the first-screen count follows the measured
screen size via a cookie. Search terms: above the fold, viewport-adaptive
loading, Lighthouse "Defer offscreen images". Client Hints
(Sec-CH-Viewport-Width) are the native alternative, but they are Chrome-only and
absent on the first visit. Re-run `install` to pick up the updated agents and packs.

## For contributors

- The release workflow builds `dashboard/dist` in a separate, unprivileged job
  and passes it to the publish job as an artifact checked against the build's
  manifest hash; publishing fails if the tarball lacks
  `dashboard/dist/index.html`. The publish job still installs nothing and runs
  no scripts.
- `canonkit install` and the commands that build the install catalog now stop
  with "The dashboard is not built" and the fix, instead of a raw `ENOENT`, when
  `dashboard/dist` is missing.

- The dashboard frontend is React + React Flow, built with Vite. `npm test`,
  `npm run test:fast` and `npm pack` build it first (`pretest`, `prepack`);
  `npm run dashboard:typecheck` checks the types. These are devDependencies
  only: installing canonkit pulls no frontend packages.
- `dashboard/THIRD_PARTY_NOTICES.md` lists the licenses of the bundled
  packages. Update it when `dashboard/src/main.tsx` imports a new one.
- The UI was checked by hand in one Chrome session (desktop and 390 px, keyboard,
  accessibility tree); there is no automated UI-level test yet.
